## F.1 Agent 基础概念与架构（8 题）

### Q1. 用大白话说清楚什么是 Agent，它和「直接调大模型」的本质区别是什么？

**真题出处**：字节跳动 / 快手 / 腾讯。

**答**：Agent 是一个**以 LLM 为决策核心、能自主决定下一步做什么、通过调用工具与环境交互、并依据反馈循环推进直到达成目标**的系统。和「一次 API 调用」的本质区别在**控制流方向**：普通应用由开发者写死调用顺序，LLM 只在固定位置生成文本；Agent 由 LLM 自己决定下一步（调哪个工具、是否终止）。因此它更像「带随机性的状态机」，测试难度、成本模型、失败模式都不同。

**追问「那 Siri 类助手算 Agent 吗？」**：关键看自主性——固定意图路由 + 单轮执行的偏 Workflow；能多步规划、动态调工具、根据结果纠错的才算 Agent。

### Q2. Agent 的基本架构由哪些核心组件构成？

**真题出处**：阿里巴巴 / 小林coding 16 题 Q2。

**答**：经典四要素 + 一个隐性运行时：

| 组件 | 职责 |
|---|---|
| LLM（决策核心） | 意图理解、任务分解、工具选择、结果判断——唯一的非确定性组件 |
| Planning（规划） | 把高层目标拆成子步骤，并根据反馈重规划（ReAct / Plan-and-Execute 等） |
| Memory（记忆） | 短期=上下文窗口；长期=跨会话持久化（向量库 / 知识图谱 / 结构化表） |
| Tools（工具） | Agent 与外部世界交互的唯一通道，边界决定能力上限 |
| **Runtime（运行时，隐性但关键）** | 循环控制、状态持久化、重试、超时、并发、日志追踪、人工介入 |

**加分点**：很多团队 Demo 做得快，但上线难——难点几乎全在运行时，不在 Prompt。

### Q3. Agent 和 Workflow 有什么区别？什么时候**不该**用 Agent？

**真题出处**：字节跳动 / 百度 / 腾讯广告 / 得物。**权威依据**：[Anthropic《Building Effective Agents》](https://www.anthropic.com/engineering/building-effective-agents)。

**答**：Workflow 的控制流由开发者**预定义**（prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer 五种常见模式）；Agent 的控制流由 LLM **动态决定**。

| 维度 | Workflow | Agent |
|---|---|---|
| 可预测性 | 高 | 低 |
| 调试 | 断点可打 | 需轨迹可观测 |
| 延迟 / 成本 | 稳定可估算 | 方差大（步数不定） |
| 适用 | 步骤固定、可枚举 | 步骤无法预先枚举、需探索 |
| 失败模式 | 单点可见 | 误差累积、跑偏、死循环 |

**不该用 Agent 的场景**：任务步骤固定、延迟敏感、单步即可解决、正确性不容探索（如金融计算）、成本约束严格、工具返回无法判断对错（没有反馈信号，Agent 只会越走越偏）。**工程路径**：单次 LLM → 固定 Workflow → orchestrator-workers → 单 Agent → 多 Agent，能解决就别往右走。

### Q4. ReAct 是什么？工作流程和优缺点分别是什么？

**真题出处**：携程 / 腾讯 / 快手。**权威依据**：[ReAct 论文（Yao et al., 2022）](https://arxiv.org/abs/2210.03629)。

**答**：ReAct = Reasoning + Acting，把「思考」和「行动」交错成 `Thought → Action → Observation` 循环，而不是先想完再做。每轮：LLM 输出思考与动作 → runtime 执行工具 → 结果作为 Observation 回灌 → 进入下一轮，直到输出 `finish` 或达到步数上限。

**为什么有效**：① 推理轨迹外化，提升决策质量且可调试；② Observation 是真实反馈，能打断幻觉链；③ 长程规划被降维成一系列局部决策。

**工程坑**：格式解析失败（优先原生 Function Calling）、上下文膨胀、死循环（见 Q40）、错误级联、终止不可靠（需显式 finish + 最大步数硬上限）。

**成本**：每轮 = 1 次 LLM 调用 + N 次工具调用，token 成本随步数近似平方增长——这是 prompt caching 能省大钱的原因（详见 Q24）。

### Q5. ReAct 和 Plan-Execute-Replan 的区别是什么？分别适用于哪些场景？

**真题出处**：美团 / 小红书。

**答**：

| 维度 | ReAct | Plan-Execute-Replan |
|---|---|---|
| 结构 | 边想边做，交错循环 | 先一次性规划，再执行，可重规划 |
| 全局视野 | 弱，易跑偏 | 强 |
| 适应性 | 强，实时反馈 | 依赖计划质量，动态环境弱 |
| 成本 / 延迟 | 步数不定、方差大 | 规划一次、更可控 |
| 适合 | 探索型、路径未知 | 步骤可预判、长任务、需用户确认计划 |

**Plan-Execute-Replan 为什么需要监管（Replanner）Agent**：计划基于先验，执行中必然遇到偏差；Replanner 在每步后判断「继续 / 修改计划 / 完成」，并设重写次数上限（如 3 次），超限升级人工。实践技巧：**计划粒度要小**（每步一个工具调用），粒度过粗会掩盖偏差。

### Q6. 除了 ReAct，还有哪些 Agent 设计范式？

**真题出处**：小林coding 16 题 Q4/Q6；Imironman Agent 专题 Q4。

**答**：

| 范式 | 结构 | 主要优势 | 主要代价 |
|---|---|---|---|
| ReAct | 交错循环 | 灵活、反馈驱动、实现简单 | 串行慢、易死循环 |
| Plan-and-Execute | 计划 + 执行 | 全局视野、成本可控、可 HITL | 计划错误难挽回 |
| [Reflexion](https://arxiv.org/abs/2303.11366) | 带反思的重试 | 失败后生成「教训」写入记忆，跨尝试改进 | 需要可靠的成功信号（单测、编译、评分） |
| [LLM Compiler](https://arxiv.org/abs/2312.04511) | Planner 产出 DAG + 并行调度 | 无依赖子任务并行，降延迟与成本 | 依赖关系识别错误会导致错误并行 |
| [ToT](https://arxiv.org/abs/2305.10601)（了解） | 树状搜索 + 自评 + 回溯 | 需探索的复杂推理 | 调用量指数级，业务性价比低 |

**收敛口径**：大多数业务 Agent 真正落地的是「ReAct / Plan-Execute + 一次 Self-Refine 迭代 + 用代码或工具做验证器」。

### Q7. 复杂任务怎么做任务拆分？为什么拆分能提升效果？

**真题出处**：小林coding 16 题 Q7。

**答**：拆分的本质是**降低单步认知负荷 + 隔离错误**。常见做法：让 LLM 先产出子任务清单（可按依赖组织成 DAG），再逐个子任务执行；每个子任务给独立的工具子集与上下文。收益：推理更聚焦、可并行、失败可局部重试；风险：拆得太碎导致上下文割裂、子任务间依赖判断错误。要点是**给每个子任务明确输入输出契约**，并保留一个汇总/校验环节。

### Q8. 企业落地 Agent 系统最大的瓶颈是什么？用 Agent 有哪些弊端？

**真题出处**：面灵AI 155 题（无公司标注）。

**答**：瓶颈排序：① **可靠性**（长链路误差累积，成功率难达标）；② **评估与归因**（效果难量化，改一处不知道是变好还是变坏）；③ **成本与延迟**（token 与 P95 远高于固定链路）；④ **权限与安全**（越权、注入、误操作）；⑤ **信任与流程**（人不敢放手，HITL 设计缺失）。弊端同理：不确定性、成本高、审计难。**判断标准**：当任务「步骤无法预枚举且有可判定的反馈信号」时，Agent 才值得用。

## F.2 工具调用：Function Calling、MCP、Skills、A2A（10 题）

### Q9. Function Calling 的原理是什么？模型如何知道该调用哪个工具？

**真题出处**：阿里巴巴 / 快手 / 京东。**权威依据**：[OpenAI Function Calling 文档](https://platform.openai.com/docs/guides/function-calling)。

**答**：**模型不执行函数，它只是生成一段符合约定格式的结构化输出（通常是 JSON），由宿主程序解析、执行，再把结果回灌。**

1. 请求里带 `tools=[{name, description, parameters(JSON Schema)}]`；
2. 模型被训练成「该调用工具时输出 `tool_calls`」；
3. 宿主解析 `name` 与 `arguments`（注意 arguments 是字符串，需二次 `json.loads`）；
4. 执行本地函数 → 以 `role="tool"` / `tool_call_id` 关联回灌 → 再次请求模型。

**要点**：`description` 的质量直接决定选对率（要写「什么时候用」和「什么时候不要用」）；三种实现路线——原生 Function Calling（推荐）、纯 Prompt 约定 + 文本解析（兼容差）、[约束解码 XGrammar](https://github.com/mlc-ai/xgrammar)（自部署场景从采样层保证 JSON 100% 合法）。

### Q10. 模型返回的 Function Call 参数格式不对，工程上怎么处理？

**真题出处**：阿里巴巴。

**答**：四层处理：① **容错解析**（剥离 markdown 代码块、容忍尾逗号，用 json5）；② **Schema 校验**（Pydantic / jsonschema，类型、必填、枚举）；③ **错误回灌**（把校验错误文本作为 Observation 让模型自我修正，通常一次即好）；④ **兜底**（重试仍失败则降级到澄清提问或人工）。根治手段是约束解码（见 Q9）。

### Q11. 并行工具调用（Parallel Tool Calling）是怎么实现的？有什么限制？

**真题出处**：Imironman Agent 专题 Q6。

**答**：模型一次响应返回多个 `tool_calls`，宿主并发执行（如 `asyncio.gather`），再把所有结果按 `tool_call_id` 一次性回灌。限制：① 只能并行**幂等、无依赖**的工具；② 写操作（转账、下单）强烈不建议并行，需串行 + 幂等键；③ 运行时要做依赖检查，防止模型错误并行；④ 并发度要限流（Semaphore），避免打挂下游；⑤ 并行省的是 wall-clock 延迟，**不省 token**。

### Q12. 注册了上百个工具，怎么降低工具调用幻觉、提升选对工具的准确率？

**真题出处**：字节跳动 / 快手（高频）。

**答**：按性价比排序：

1. **分层 + 工具路由（Tool RAG）**：按领域分组，小模型/分类器先路由，只注入命中的 5–10 个工具；
2. **命名与描述治理**：`namespace_action` 命名、写清适用与不适用场景、给参数示例；
3. **工具收敛合并**：把同一资源的多操作合并为带 `action` 枚举的工具；
4. **元工具 / Code as Action**：暴露 `run_python` / `execute_sql`，让模型写代码组合调用（需沙箱）；
5. **多 Agent 分工**：每个子 Agent 只挂自己领域的工具。

**量化口径**：构造「(query, 正确工具)」评测集（含易混淆对照对），报工具名 top-1 准确率 + 参数填充准确率。

### Q13. MCP 是什么？它解决了什么问题？由哪几部分组成？

**真题出处**：字节跳动 / 腾讯 / 京东 / 阿里巴巴 / 抖音。**权威依据**：[MCP 规范](https://modelcontextprotocol.io/specification/)。

**答**：MCP（Model Context Protocol）是 Anthropic 开源的开放协议，用来标准化 LLM 应用与外部数据源/工具之间的连接——**把 M×N 个适配器问题降成 M+N**。

架构分三层：**Host**（LLM 应用本体）、**Client**（与某个 Server 1:1 连接）、**Server**（暴露能力，本地 stdio 或远程 Streamable HTTP）。Server 暴露三种原语：

| 原语 | 控制方 | 说明 |
|---|---|---|
| Tools | 模型 | 可执行函数，可能有副作用 |
| Resources | 应用 | 只读上下文数据 |
| Prompts | 用户 | 预设提示模板 / 工作流入口 |

**坑**：协议不等于权限（Server 内容不可无脑信任）；工具数量不会因 MCP 变少；远程 MCP 的鉴权与多租户隔离要自己设计。

### Q14. MCP 与 Function Calling 有什么区别？

**真题出处**：字节跳动 / 快手 / 货拉拉 / 百度。

**答**：**不是替代关系，是分层关系**。Function Calling 解决「模型如何表达要调哪个函数」（模型侧调用表达）；MCP 解决「工具如何被发现、连接、复用」（工程侧供给协议）。MCP Server 暴露的 Tools 最终仍要以 Function Calling 的 schema 形式呈现给模型。

### Q15. MCP 的通信方式有哪些？SSE 和 WebSocket 怎么选？

**真题出处**：阿里巴巴；小林coding 工具调用 16 题 Q13/Q14。

**答**：MCP 传输层主要是 **stdio**（本地子进程，简单、常用于本地工具）与 **Streamable HTTP**（远程，已取代早期的 HTTP+SSE 方案）。通用选型：**SSE** 基于 HTTP 单向（服务端→客户端）推送，简单、穿代理友好，适合「模型流式输出」这类单向下行场景；**WebSocket** 是全双工长连接，适合双向实时交互（如人工实时介入）。语音/视频链路另考虑 WebRTC（抗弱网更好）。

### Q16. MCP 和 Skills 有什么区别？Function Call、MCP、Skill 三者的边界在哪？

**真题出处**：TikTok / 京东 / 字节跳动 / 美团 / 腾讯 / 阿里云 / 小红书 / B站（2026 最热对比题）。

**答**：

| 概念 | 定位 | 解决的问题 |
|---|---|---|
| Function Calling | 模型侧的**调用表达** | 模型怎么把「我要调工具」说清楚 |
| MCP | 工程侧的**连接协议** | 工具/数据源怎么被标准化地发现、连接、复用 |
| Skill | 能力侧的**打包与披露** | 把领域流程、指令、脚本、资源打包，按需加载 |

一句话：**Function Calling 是「怎么说」，MCP 是「怎么接」，Skill 是「怎么装」**。Skill 通常是一个带说明的目录（指令 + 脚本 + 资源），Agent 先只看到元数据，命中后才加载正文。

### Q17. Skill 的渐进式披露（Progressive Disclosure）是怎么实现的？为什么能省 token？

**真题出处**：美团 / 网易 / 快手 / 腾讯（2026 新考点）。

**答**：渐进式披露是**分层加载**：第一层只把每个 Skill 的元数据（名称、一句话描述、触发条件）放进上下文；模型判断需要某个 Skill 时，才把它的完整指令、示例、脚本接口加载进来；真正执行时再按需读文件或跑脚本。因为绝大多数轮次只用到少数 Skill，**大量 Skill 的正文与资源永远不会进入上下文**，token 消耗随之下降；同时也缓解了「工具/指令太多导致模型注意力被稀释」的问题。

### Q18. A2A 和 MCP 是什么关系？多 Agent 之间的通信协议应该怎么设计？

**真题出处**：阿里千问 / 字节跳动。**权威依据**：[A2A 协议](https://a2a-protocol.org/latest/)。

**答**：MCP 是**垂直**的（Agent → 工具/数据），A2A 是**水平**的（Agent → Agent）。A2A 的核心概念：**Agent Card**（描述能力、端点、鉴权的元数据，供发现）、**Task**（有生命周期的任务对象：submitted / working / input-required / completed / failed）、**Message & Artifact**，支持 SSE 流式与推送。

**选型建议**：内部同构系统且你能控制所有 Agent，直接走函数调用/内部 API 更简单；跨组织、跨厂商、需要动态发现时才引入 A2A。设计通信协议时至少考虑：消息幂等、超时与重试、状态机、错误语义、鉴权与隔离。

### Q19. 工具调用报错、长时间无响应、连续失败时，重试与异常隔离策略怎么设计？

**真题出处**：快手 / 蔚来。

**答**：错误分类处理——**瞬时错误**（限流、网络抖动）指数退避重试；**参数错误**回灌模型自修；**权限/业务错误**不重试，直接告知模型换路径；**超时**设单次超时 + 总预算；**连续失败**触发熔断，降级到澄清提问或人工。隔离上：每个工具独立超时与并发池，失败结果以结构化错误回灌（错误也是 Observation），避免一个工具拖垮整个 loop。

### Q20. Agent 的退出/终止条件怎么设计？只靠最大轮次够吗？

**真题出处**：字节跳动 / 快手。

**答**：不够。终止条件至少四层：① 显式 `finish` 动作（模型自认为完成）；② 最大步数 / token 预算 / 时间预算硬上限；③ **无进展检测**（重复调用同一工具同一参数、输出高度相似）；④ 外部校验（任务完成判定器、单测、schema）。触顶后的行为要预先定义：返回部分结果 + 说明、升级人工、或降级到固定 Workflow。

## F.3 记忆管理与上下文工程（8 题）

### Q21. Agent 的短期记忆和长期记忆如何实现、如何区分？

**真题出处**：京东 / 携程 / 美团 / 京东科技 / 滴滴。**权威依据**：[MemGPT](https://arxiv.org/abs/2310.08560)、[CoALA 记忆分类](https://arxiv.org/abs/2309.02427)。

**答**：**短期（工作记忆）= 当前会话上下文**，核心矛盾是「窗口有限 vs 信息无限增长」，策略有四：滑动窗口、结构化摘要（用户目标/已确认事实/未决问题/已执行动作）、分层记忆（MemGPT：主上下文 ↔ 外部存储，模型用工具自己换入换出）、选择性保留（重要性打分，偏好与约束永不压缩）。

**长期记忆**跨会话持久化，分语义（事实）、情节（经历）、程序性（技能）三类，落地为向量库 / 知识图谱 / 结构化表 / 托管服务（Mem0、Zep 等）。**写入要触发式**（会话结束、用户显式要求、检测到稳定新事实），且必须做去重与冲突消解（ADD/UPDATE/DELETE）；**检索要多路**（向量 + 关键词 + 时间衰减 + 重要性 + rerank），带时间戳注入；**遗忘是合规要求**（TTL、衰减、主动删除）。

### Q22. 长期记忆和 RAG 有什么区别？为什么记忆要分长短期？

**真题出处**：阿里千问 / 通义。

**答**：两者都靠检索，但**对象与生命周期不同**：RAG 面向**静态知识库**（文档、知识），写入由数据管道决定，读多写少；记忆面向**会话状态与用户事实**（偏好、经历、约定），每轮可能写入、需要更新与遗忘。分长短期是因为成本与延迟：把全部历史都塞进窗口既贵又稀释注意力；应按「稳定性」分层——稳定事实进 system prompt 或长期记忆，动态信息留在会话窗口。

### Q23. 记忆如何召回？如何避免不同问题召回的记忆相互污染？

**真题出处**：字节跳动 / 小红书 / 蔚来。

**答**：召回不能只看向量相似度，生产上常用**多路召回**（向量 + BM25 + 时间 + 重要性）再 rerank；注入时**带来源与时间戳**，并给记忆标类型与置信度。防污染手段：按用户/会话/租户做**命名空间隔离**；写入前去重与冲突消解（「用户换工作了」应 UPDATE 旧事实而非并存）；检索时按当前任务做**相关性过滤**，低置信记忆不注入；定期审计与清理。

### Q24. 上下文工程（Context Engineering）应该怎么设计？和 Prompt Engineering 什么关系？

**真题出处**：高德 / 字节跳动。**权威依据**：[Anthropic《Effective context engineering for AI agents》](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

**答**：Prompt Engineering 关注「指令怎么写」；Context Engineering 关注「在有限窗口里放什么信息」——它是前者的超集。可归纳为三类操作：

- **写入（Write）**：把信息存到窗口外（scratchpad、文件系统、记忆库），需要时按引用取回；
- **选择（Select）**：只拉当前步骤真正需要的内容（检索、工具路由）；
- **压缩（Compress）**：摘要、裁剪、丢弃冗余工具返回。

**手法清单**：工具结果在工具层就 trim + 字段白名单；**prompt caching** 缓存不变前缀（system prompt、工具定义、长文档）——所以不要把时间戳、随机 ID 放进前缀；任务状态外置到固定位置（LangGraph 状态机思路）；子 Agent 上下文隔离，只回传结论摘要；Just-in-time 检索，不预加载全部文档。

### Q25. 上下文压缩应该放在链路的哪一步？先压缩再向量化，还是反过来？

**真题出处**：字节跳动 / 小红书。

**答**：分场景：**写长期记忆**时，通常是先结构化摘要、再向量化存储（省空间、检索准），但**原始对话要另存**以便审计与重放；**RAG 文档入库**时不要为了省 token 压缩再向量化——检索依赖原文粒度，压缩会损失可检索性，应保留原文、在「注入上下文前」才裁剪/摘要。压缩的通用原则：保留决策与结论，丢弃冗余的工具原始返回；压缩操作放在「即将超预算」时增量执行，而不是一次性大段截断。

### Q26. 为什么上下文越长，模型结果反而越不稳定？

**真题出处**：面灵AI 155 题（字节跳动 / 蔚来追问）。

**答**：**位置敏感**（lost-in-the-middle，[论文](https://arxiv.org/abs/2307.03172)）+ 注意力稀释：模型对上下文中部信息的利用显著弱于头尾，且内容变长后整体检索与推理准确率下降。工程对策：关键指令与关键信息放**头尾**；对长上下文做选择而非全塞；结构化组织（清晰分隔、标签）；用 prompt caching 降低重发成本；必要时用「分块处理 + 汇总」代替超长单次输入。

### Q27. 快到上下文窗口阈值时，如何避免一次性大段压缩打断体验？大结果卸载怎么实现？

**真题出处**：字节跳动 / 蔚来。

**答**：采用**增量压缩**：每轮维护一个 token 预算，超出时只把最老的一段摘要化（后台进行，不阻塞当前轮），保留最近 K 轮原文与「固定记忆块」。**大结果卸载**：工具返回的大对象（整页 HTML、大 JSON、长文档）不放进上下文，只放摘要 + 引用 key，存到对象存储/Redis/文件；模型需要细节时用工具按引用读取（offload + reference）。配合 checkpoint 保证压缩与卸载过程可恢复。

### Q28. 多轮长任务如何避免「任务目标迷失」？

**真题出处**：字节跳动。

**答**：三层防线：① **状态外置**——把「原始目标、已完成、待办、约束」维护成结构化状态（状态机 / TODO 文件），每轮重写进上下文固定位置，而不是让模型从长轨迹里自己推断；② **阶段性复述**——在关键节点让模型复述目标与当前进度，与初始目标做对比（可用于自动校验）；③ **子任务收口**——每个子任务完成后产出结构化结论并写回状态，避免中间过程污染主线。

## F.4 多智能体协作与编排（6 题）

### Q29. 多 Agent 协作有哪些模式？相比单 Agent 的优势是什么？

**真题出处**：阿里巴巴 / 美团 / 字节跳动。

**答**：主流模式：

| 模式 | 说明 | 适用 |
|---|---|---|
| Supervisor / 分层 | 主 Agent 拆解、分派、汇总，子 Agent 互不直接通信 | 生产级首选，可控 |
| 角色分工（Crew） | 研究员/写手/审稿人按流水线协作 | 可流程化的任务 |
| 辩论 Debate | 多 Agent 独立作答、互相批判收敛 | 降低单模型偏差 |
| 群聊 GroupChat | 共享消息池 + speaker 选择 | 灵活但易发散、贵 |
| Handoff | 交接控制权，同一时刻一个活跃 | 客服分流等轻量场景 |

**优势**：上下文隔离（每个子 Agent 只处理自己那段繁杂过程，主 Agent 保持干净）、并行提速、职责与权限可分。**注意**：多 Agent 不是免费午餐，需要评测证明。

### Q30. 主 Agent 如何动态识别并选择子 Agent？子任务结果如何回收？

**真题出处**：美团 / 蔚来。

**答**：维护**子 Agent 注册表**（能力描述 + 输入输出契约 + 权限），主 Agent 用意图/能力匹配（LLM 路由或小模型分类）动态选择，而不是写死 if-else。结果回收：子 Agent 完成后返回结构化结果（状态、产物引用、所用工具、成本），主 Agent 在**汇总节点**合并并校验；超时或失败由主 Agent 决定重试、换 Agent、拆更小步骤或升级人工。

### Q31. 多个 Agent 结论不一致时如何处理？

**真题出处**：京东。

**答**：按成本递增：① 若可判定（有标准答案/单测/数据源），用**程序化校验**直接裁决；② **投票 / 辩论**：让分歧 Agent 各给证据，多轮收敛；③ **仲裁 Agent + rubric**：裁判按明确评分标准裁定，先给理由再给结论；④ 仍不一致则**保留分歧上报人工**（不要强行合并出错误结论）。关键原则：能用代码判的不用 LLM 判。

### Q32. 多 Agent 用异步消息通信怎么设计？失败有哪些兜底？

**真题出处**：蔚来 / 字节跳动（Markdown 传任务如何防错误传播）。

**答**：消息结构建议包含：任务 ID、父任务 ID、发/收方、状态（submitted/working/input-required/completed/failed）、产物引用、重试次数、幂等键、截止时间。兜底：超时重投、幂等消费防重复执行、失败回退到上级或备用 Agent、死信队列 + 人工兜底、全链路 trace。用 Markdown 传递任务时要**先校验任务契约**（字段、目标、验收标准），拆分错误必须在校验节点拦截，不能顺链放大。

### Q33. 多个 Agent 如何做到完全隔离（上下文、权限、存储）？

**真题出处**：字节跳动 / 蚂蚁集团。

**答**：上下文隔离——每个子 Agent 独立会话与窗口，只通过显式消息传递结果；权限隔离——每个 Agent 绑定最小权限凭证（只读/可写分离、按工具与数据域授权），凭证不跨 Agent 复用；存储隔离——按租户 / 会话 / Agent 做命名空间，跨 Agent 数据通过受控接口而非共享内存传递；再加统一审计（哪个 Agent 在何时动了什么）。

### Q34. 多智能体是否真的能提升效率？怎么证明、怎么评估？

**真题出处**：字节跳动（高频追问）。

**答**：不能默认提升。做法：**同一评测集上做对照实验**——单 Agent vs 多 Agent，比较端到端成功率、pass^k、延迟、单任务 token 成本、失败模式分布；多 Agent 的合理收益通常来自「上下文隔离 + 并行 + 权限分工」，如果任务本身是线性的、上下文也不长，多 Agent 往往只增加成本和误差传播。汇报时必须给口径（测试集、次数、成本口径），否则「效率提升 X%」经不起追问。

## F.5 评估、幻觉与可观测（8 题）

### Q35. Agent 评估体系包括哪些维度？如何衡量 planning 能力与 hallucination rate？

**真题出处**：阿里巴巴 / Shopee / 小红书 / 字节跳动。**权威依据**：本笔记[第 6 章](../part1-basics/06-agent.md)、[Anthropic《Demystifying evals for AI agents》](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

**答**：**不能只看成功率**。维度至少六类：最终结果（success rate）、过程质量（轨迹、工具调用正确性、progress rate）、可靠性（pass^k）、成本（token/单任务成本）、延迟（P95）、安全（越权/注入/高危拦截率）。

- **Planning 能力**：用需要多步规划的任务集，看计划是否可行、步骤数是否偏离、重规划次数、最终成功率；也可单独评测「计划质量」（人工或 judge 按 rubric）。
- **Hallucination rate**：先定口径——分子通常是「与权威来源冲突或无法被给定证据支持的陈述数」，分母是「总事实性陈述数」；用人工标注的黄金集校准，再用 LLM judge 批量跑，报告 judge 与人工的一致性；**口径不变才能纵向比较**。

### Q36. Agent 项目应该统计哪些指标？

**真题出处**：字节跳动 / 通义。

**答**：业务层：任务成功率、完成率、人工接管率、用户纠错率；过程层：平均步数、工具调用成功率、工具选择准确率、无效调用占比、重试率；工程层：P50/P95 延迟、单任务 token 成本、每轮缓存命中率、错误分类分布；质量层：pass^k、幻觉率、安全拦截率。原则：**每个数字都要能讲清「怎么算的、测试集多大、口径定义」**——面试官必追。

### Q37. pass@k 和 pass^k 有什么区别？为什么对 Agent 特别重要？

**真题出处**：结合[第 3 章](../part1-basics/03-model-level.md)与[第 6 章](../part1-basics/06-agent.md)（τ-bench / HAL 口径）。

**答**：pass@k = k 次里**至少一次成功**（能力上限）；pass^k = k 次**全部成功**（可靠性）。Agent 是长链路随机系统，单次成功率会被「侥幸通过」拉高，pass^k 才能暴露稳定性问题；对生产来说「每次都能完成」比「偶尔能完成」重要得多。报告时两者都要给，并说明 k 与任务集。

### Q38. 轨迹评估 / progress rate 是什么？怎么落地？

**真题出处**：小林coding 16 题 Q17；AgentBoard 基准。

**答**：把 Agent 的**操作序列**当评分对象：progress rate 衡量「完成了多少关键里程碑（子目标）」，即使最终失败也能给出部分分，便于区分「完全跑偏」和「差最后一步」。落地：为任务定义里程碑清单与判定器（状态检查 / 工具结果检查），跑完对轨迹逐项判定；配合工具调用正确率、无效步骤数一起看。权威参考：[AgentBoard](https://arxiv.org/abs/2401.13178)。

### Q39. 线上 Agent 一直调工具但不返回结果，怎么 Debug？如何区分是 Prompt、模型、工具还是逻辑问题？

**真题出处**：字节跳动 / 腾讯混元。

**答**：先看 **trace**（每步的输入、模型输出、工具参数、返回、耗时、token），然后**隔离变量**：① 固定同一输入重放，定位稳定复现点；② 组件级测试——单独测工具（mock 输入）、单独测 Prompt（给定上下文看输出）、单独测路由（选对工具吗）；③ 消融——换模型、换 Prompt、缩小工具集，看哪一变好；④ 看错误分布——参数错=描述/校验问题，重复调用=终止与去重问题，工具超时=下游问题。结论要落到「组件 + 具体改动」。

### Q40. Agent 死循环 / 无限调用的原因及解决方案？为什么要设计三层防护？

**真题出处**：字节跳动 / 快手。

**答**：原因：模型陷入「同样的动作、同样的结果」；终止条件缺失；工具失败信息不充分导致反复重试。三层防护：**内层**——重复检测（对 `(tool, args)` 做哈希 + 滑动窗口，重复即注入提示「你已调过，请换思路」）；**中层**——步数/时间/token 预算硬上限 + 无进展检测；**外层**——熔断与降级（转人工、返回部分结果），并保证副作用操作幂等。三层缺一不可：只限步数会浪费成本，只做检测会漏掉慢速打转。

### Q41. 如何建立 Agent 的可观测性（轨迹、指标、回放）？

**真题出处**：通义；本笔记[第 9 章](../part2-enterprise/09-tooling.md)。

**答**：以 **trace 为第一等公民**：每次运行生成 session trace，span 覆盖 LLM 调用、工具调用、检索、审批，记录输入输出、token、耗时、成本、错误；指标（成功率/延迟/成本/工具错误率）从 trace 聚合；支持按 session 回放与对比；把线上失败样本回灌评测集。标准侧关注 OTel GenAI Semantic Conventions，工具侧 LangSmith / Langfuse / Phoenix / Braintrust 均可提供类似能力。

### Q42. 幻觉率怎么定义和计算？「降幻觉 X%」的数字是怎么量化出来的？

**真题出处**：字节跳动 / 美团（检测 Agent 自身幻觉怎么办）。

**答**：先定口径再算数：例如「抽 300 条真实 query，人工判定事实性陈述中不支持的条数；不支持数 / 总事实性陈述数 = 幻觉率」，同时报告置信区间；改进后用**同一评测集、同一口径**复测。若用检测 Agent：用人工标注报检测器的 precision/recall，并定期复标防漂移；链式幻觉则要求每步输出带证据引用、下游只接受有引用的事实。

## F.6 安全、兜底与可靠性（7 题）

### Q43. Prompt Injection / Indirect Prompt Injection 是什么？如何防范？

**真题出处**：钉钉 / 小红书 / 字节跳动。**权威依据**：[Greshake et al., 2023](https://arxiv.org/abs/2302.12173)、本笔记[第 8 章](../part1-basics/08-safety-compliance.md)。

**答**：直接注入是用户输入里塞「忽略以上指令」；**间接注入**是恶意指令藏在 Agent 会读取的外部内容里（网页、文档、工单、工具返回）。防范：① 信任边界——外部内容只当**数据**不当**指令**，用清晰分隔与标签；② 最小权限——工具白名单、只读优先、写操作需审批；③ 输出与动作校验（能执行的动作不因一段文本就放开）；④ 高危操作强制人工确认；⑤ 审计与回放。注意：**没有 100% 防住的方案**，工程目标是降低概率 + 限制爆炸半径。

### Q44. Agent 如何做权限控制避免越权？哪些内容必须人工审核？

**真题出处**：腾讯 / 京东 / 蚂蚁集团 / 唯品会。

**答**：身份与权限：Agent 使用**受限身份**（不是超级账号），按用户授权范围拿最小凭证，工具粒度授权（读/写/转账/重启分开）；敏感操作增加二次确认或双人复核；全量审计（谁/何时/对谁/做了什么/依据哪条指令）。**必须人工审核**：资金与支付、对外发送（邮件/公告）、生产变更与重启、删除类操作、涉及未成年人/隐私数据的处理。原则：**只读可放手，有副作用必须可控**。

### Q45. 沙箱机制如何实现？

**真题出处**：B站（系统设计追问）。

**答**：目标是把「模型生成的代码 / 命令」限制在可丢可限的边界内：进程或容器级隔离（gVisor / Firecracker / Docker）、网络默认拒绝 + 白名单、文件系统只读挂载 + 临时可写层、资源限额（CPU/内存/磁盘/超时）、无宿主机凭证、执行留痕。配合命令/URL 白名单、危险模式拦截（rm -rf 等），并定期回收环境。

### Q46. 高危操作（真实资金、重启机器）怎么管控？

**真题出处**：蚂蚁集团 / 唯品会 / 字节跳动。

**答**：① **默认只读诊断**，变更类动作走审批通道；② **干跑（dry-run）**先给影响面与回滚方案；③ 幂等键 + 可回滚/补偿（Saga）；④ 金额、次数、时间窗的硬限额；⑤ 双人复核 / 二次认证；⑥ 完整审计与事后核对。技术上把「提议」与「执行」解耦：Agent 产出变更计划，执行器在授权后落地。

### Q47. HITL：触发人工确认时 Agent Loop 处于什么状态？状态怎么暂停、暂存和恢复？

**真题出处**：蔚来 / 字节跳动。

**答**：触发审批时 Loop 进入**挂起（interrupt）**而不是结束：把当前图状态（消息、计划、已完成步骤、待执行动作、上下文引用）持久化为 checkpoint，与 thread/session 绑定，推送给审批人；审批通过后从该 checkpoint 恢复执行（可带上审批附言），拒绝则走回退分支（修改计划/终止）。要点：状态必须**可序列化**（大对象存外部、上下文只存引用）、操作**幂等**（恢复不重复副作用）、审批有 TTL 与超时策略。LangGraph 的 checkpointer + interrupt 是典型实现。**权威依据**：[LangGraph 文档](https://github.com/langchain-ai/langgraph)。

### Q48. Agent 执行到中间某阶段出异常，如何断点恢复？整体兜底方案是什么？

**真题出处**：字节跳动 / 京东。

**答**：断点恢复 = checkpoint + 幂等 + 可重放：每个 super-step 后持久化状态；恢复时从最近 checkpoint 继续，已完成的副作用步骤靠幂等键去重。兜底层次：重试（瞬时错误）→ 换路径（模型重规划）→ 降级到固定 Workflow（确定性子任务）→ 返回部分结果并说明 → 升级人工。兜底方案要预先写进设计文档并演练，而不是出事再想。

### Q49. Agent 的执行过程要不要向用户透明展示？展示到什么粒度？

**真题出处**：面灵AI 155 题。

**答**：要，但分层。面向用户展示「关键里程碑 + 正在做什么 + 是否需要输入」，不展示冗长的内部 Thought 全文（可折叠）；对可确认的操作给出预览与撤销入口；对失败给可操作的错误说明与转人工通道。透明度的目标是**建立信任与可纠错**，不是把 trace 原样倾倒给用户。

## F.7 系统设计题（4 题）

> 系统设计题的通用答题骨架：**澄清需求与成功指标 → 画主链路 → 拆组件与状态 → 失败与安全兜底 → 评测与迭代**。下面每题给「考点 + 关键取舍」。

### Q50. 设计一个 AI 客服 Agent：任务怎么拆？记忆怎么存？工具调用失败怎么兜底？

**真题出处**：阿里巴巴 / 通义 / 字节跳动（几乎必考）。

**答**：主链路：意图识别与分类 → 知识问答走 RAG（产品库/政策库）→ 业务操作走工具（订单、物流、退款）→ 高风险操作转人工。设计要点：① 任务拆分按「可判定成功」切分，每步有验收；② 记忆分三层——会话摘要（当前诉求/已确认信息）、用户长期偏好、业务状态（订单号等外置到系统，不进模型）；③ 工具失败分层兜底（重试→自修→澄清→人工），退款等写操作幂等 + 审批；④ 核心成功指标：一次解决率、转人工率、满意度、单会话成本、P95 延迟；⑤ 评测：真实工单回灌 + 人工/裁判评分。

### Q51. 设计一个 AI 代码 Review / 自动 PR Agent：怎么保证它只提意见、不直接改代码？

**真题出处**：字节跳动 / B站。

**答**：权限上**只读仓库 + 只能产出评论/建议 diff**，不能直接 push；流程：拉取 PR diff → 静态检查与测试先跑 → 模型按 rubric 评审（正确性、边界、安全、可维护性）→ 输出分级意见（必须改/建议/疑问）并附证据（行号、引用）；修复建议以 patch 形式给出、由人决定是否应用。评估用历史 PR 回放：看意见采纳率、误报率、漏报率；沙箱中跑测试验证建议。安全性：防止把恶意 PR 内容当指令（间接注入）。

### Q52. 设计一个运维 / 故障排查 Agent：支付接口超时，它怎么跑完整套排查流程？高危操作怎么管控？

**真题出处**：字节跳动 / 唯品会。

**答**：排查流程按 runbook 工具化：查监控与告警 → 看依赖链路（网关、支付通道、DB）→ 查最近变更 → 日志检索与聚类 → 给出根因假设并验证（每一项都有对应只读工具）。**高危操作管控**：重启/回滚等变更不直接执行，Agent 产出「变更计划 + 影响面 + 回滚方案」，走审批后由执行器落地；限额、幂等、审计、双人复核同上（Q46）。用历史故障做评测集，看平均定位时间与根因命中率。

### Q53. 设计多 Agent 文献调研系统：三个核心风险是什么，分别怎么应对？

**真题出处**：面灵AI 155 题（字节跳动等）。

**答**：① **事实错误 / 引用造假**——要求每句话带来源引用，检索层保存原文快照，引用需可回溯校验（能程序化校验的引用必须校验）；② **成本与延迟失控**——设预算（页数、token、工具次数、总时长），并行化 + 缓存，超预算降级（减少轮次或提前交付）；③ **误差传播 / 目标漂移**——子任务明确输入输出契约 + 结果校验节点，主 Agent 定期复述目标与进度，失败子任务可回退重做。产出汇总时保留分歧与不确定性标注。

## F.8 手撕代码题（4 题）

> 2026 下半年新趋势：脱离框架手写 Agent 组件。面试时先讲清接口与边界，再写主干，最后补异常与终止条件。

### Q54. 脱离任何框架，手写一个最小 ReAct Agent

**真题出处**：面灵AI 155 题（2026 下半年高频）。

**答**：组件与逻辑：

```python
def react_agent(query, tools, llm, max_steps=10):
    trace = []
    for _ in range(max_steps):
        out = llm(build_prompt(query, tools, trace))   # 输出 Thought/Action
        thought, action, args = parse(out)
        if action == "finish":
            return args["answer"]
        try:
            obs = tools[action](**args)                # 工具注册表
        except Exception as e:
            obs = f"工具执行失败：{type(e).__name__}: {e}"   # 失败也是 Observation
        trace.append((thought, action, obs))
    return escalate(query, trace)                       # 超步数兜底
```

讲清五个点：工具注册（schema + 描述）、Prompt 组装、输出解析容错、循环与终止条件、异常与兜底。

### Q55. 手写一个死循环检测器

**真题出处**：面灵AI 155 题。

**答**：对每次工具调用生成签名 `hash(tool_name + normalized_args)`，维护最近 N 步的签名窗口；同一签名出现次数超过阈值，或连续 M 步无状态变化（无新信息产出），判定为死循环。返回判定结果 + 建议动作（注入「换思路」提示 / 中断转人工）。注意参数要先规范化（排序 key、去空白），避免因同义参数漏检。

### Q56. 手写上下文压缩 / 滑动窗口摘要逻辑

**真题出处**：面灵AI 155 题。

**答**：给定消息列表和 token 上限：① 永远保留 system prompt 与固定的「用户偏好/约束」块；② 从最老的消息开始，累积到超过预留预算时，把这一段交给 LLM 生成**结构化摘要**（目标 / 已确认事实 / 已做动作 / 未决问题）；③ 保留最近 K 轮原文；④ 大工具结果替换为引用占位符（`{ref: 对象存储 key, 摘要}`）；⑤ 输出组装为 `[system] + [摘要] + [最近 K 轮] + [当前输入]`。测试用例覆盖：正常、恰好超限、工具结果超大、摘要本身超长。

### Q57. 手写一个多 Agent 消息路由器

**真题出处**：面灵AI 155 题。

**答**：维护 `{agent_name: capability_description}` 注册表；对输入任务用 LLM 或小模型做能力匹配得到目标 Agent；发送任务（带任务 ID、超时、幂等键），等待结果；超时重试（有限次）后回退到备用 Agent 或主 Agent 兜底；记录路由日志用于评测路由准确率。面试加分点：说明「路由错误」是独立指标，需要专门构造易混淆任务测试。

## F.9 项目深挖与软性题（5 题）

### Q58. 深挖简历里的 Agent 项目：落地逻辑、核心难点、指标怎么量化？

**真题出处**：所有大厂的主线问题（占比最高）。

**答**：用 STAR + 技术决策组织：背景与目标 → 为什么用/不用 Agent（对照 Workflow 方案）→ 架构与关键取舍（模型、工具、记忆、编排）→ 难点与踩坑 → **指标与口径**（测试集多大、成功率/成本/延迟怎么测、对照组是什么）→ 后续改进。准备被追问三层：为什么这么选、不做另一个方案的理由、出了问题怎么发现和修复。**红线**：简历上的每个数字都要能讲清算法与测试集。

### Q59. 没有 Agent 项目经历怎么办？

**真题出处**：面灵AI FAQ / 代码随想录 FAQ。

**答**：搭一个最小可讲的项目：ReAct Agent（工具注册、循环、终止、异常）+ 记忆管理 + 上下文压缩 + 一个小评测集（20–50 例，人工 pass/fail）。重点是**记录踩坑与前后对比数据**（加了压缩后 token 降多少、成功率变化），这些细节比项目规模更能说服面试官。工程背景可迁移：把测开/后端经验映射到「运行时、可观测、回归门禁、灰度」上讲。

### Q60. 在工程实践中，为什么有时选择「手搓」Agent，而不是直接用成熟框架？

**真题出处**：小林coding 16 题 Q13。

**答**：框架适合快速验证，但生产常手搓核心运行时，原因：① 可控性——循环、状态、重试、超时策略需要精细控制；② 可调试与可观测——黑盒抽象反而增加定位成本；③ 依赖风险——框架 API 变动、停更、锁定；④ 成本——框架的默认行为（如自动重试、全量历史）可能很贵。折中：用框架搭原型，核心 runtime 自研或深度定制，评测与 trace 一体化。

### Q61. Prompt Engineering、Context Engineering、Harness Engineering 三者什么关系？

**真题出处**：钉钉 / 字节跳动（2026 新晋考点）。

**答**：层层外扩——**Prompt**：单次指令怎么写；**Context**：每轮往窗口里放什么（选择/压缩/记忆）；**Harness**：包住模型与循环的整个工程外壳（工具、运行时、状态、权限、护栏、评测、可观测）。Harness 概念火起来是因为模型能力趋同后，**产品差距转移到外壳工程**：同一个模型，harness 好坏决定任务成功率与成本。回答时结合自己的项目讲「外壳里做了什么」。

### Q62. AI 编程中的 Plan 模式和 Agent 模式有什么区别？怎么避免 AI 改坏历史功能？

**真题出处**：小红书 / 阿里巴巴 / 快手。

**答**：Plan 模式先产出可审阅的计划（不落地修改，便于人确认与纠偏）；Agent 模式自主执行多步改动。防「改坏」：小步提交 + 每次改动跑测试（把 CI/单测作为验证器）；改动前先让模型复述影响面；限制权限（不能直接推主干）；用 diff 审查 + 回归门禁；对不确定的改动保留回滚点。**核心**：让验证器（测试）而不是模型自评来判定对错。

## F.10 一页速查：高频答案卡

| 问题 | 30 秒答案 |
|---|---|
| Agent vs Workflow | 控制流：LLM 动态决定 vs 开发者写死；能 Workflow 就别 Agent |
| ReAct 循环 | Thought → Action → Observation；终止靠 finish + 硬上限 |
| Plan-Execute 为什么要 Replanner | 计划基于先验会偏差，需每步判断继续/改计划/完成 |
| Function Calling 本质 | 模型只产 JSON，宿主解析执行后回灌 |
| MCP 是什么 | 连接协议，把 M×N 适配降成 M+N；Host/Client/Server + 三原语 |
| FC / MCP / Skill | 怎么说 / 怎么接 / 怎么装 |
| Skill 渐进式披露 | 先只暴露元数据，命中后加载正文，省 token |
| A2A vs MCP | 水平（Agent↔Agent）vs 垂直（Agent→工具） |
| 长期记忆 vs RAG | 状态与用户事实（可写可忘）vs 静态知识库（读多写少） |
| 上下文越长越好吗 | 否；lost-in-the-middle，关键信息放头尾 |
| pass@k vs pass^k | 至少一次成功 vs k 次全对；Agent 看 pass^k |
| progress rate | 关键里程碑完成度，失败也给部分分 |
| 幻觉率怎么算 | 先定口径（不支持的陈述 / 总事实陈述），人工校准 judge，同口径复测 |
| 死循环三层防护 | 重复检测 / 预算上限 / 熔断降级 |
| 间接提示注入 | 外部内容只当数据；最小权限 + 写操作审批 + 审计 |
| HITL 暂停恢复 | checkpoint 持久化状态 → 审批 → 幂等恢复 |
| 手撕最小 ReAct | 工具注册、Prompt 组装、解析容错、循环终止、异常兜底 |
| 项目深挖 | 每个数字都要能讲清口径、测试集与对照组 |

**备考建议**：别背答案，练「判断力 + 项目叙事」——每道概念题都准备一句「我们项目里具体怎么做的、效果怎么量化的」；每个技术选型都准备「为什么不用另一个」。
